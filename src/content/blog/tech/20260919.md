> 该报销单审计智能体项目在设计时考虑到需要严格按照步骤流程并且完整对来自应用侧多变多样的规则进行审计，选择了workflow的设计，并未采用llm+skill这种以llm自主决策的模式，确保结果可溯源可审计。该阶段的重点在于事后审计，但是设计上也考虑到了后续需要用于事前审计。技术上采用langgraph框架进行编排，利用send能力进行规则动态分发并行。整体编排其实简单易懂，节点设计为获取oa信息→ocr识别→规则获取→数据处理→任务分发并行→单条规则审计→总结节点。 其他部分另外的笔记再说，本篇主要记录这两天关于单条规则审计在测试环境时发现的问题和解决方式。

## 初始设计

该节点初始设计时，重点在状态和输出结构上进行了设计。
由于规则审计除了要输出是否符合规则或者有风险以外，还需要给出响应的理由、数据来源、支撑材料甚至在证据不足的情况下要能够指出缺少哪些数据，以便提交人员可以补充材料，因为是动态的而且要便于前端进行展示就涉及到很多列表（但是现在想想如果这些列表选择采用指定符号分割文本，后续输出给应用侧时再做数据处理转成列表会不会对llm更友好）。

对于llm利用```with_structured_output```指定结构化输出，因本地开发采用Deepseek，测试生产采用的是Qwen，无法直接使用openai的"json_schema"模式，仅能采用"json_mode"，并且需要在prompt里面显式表示json结构（关于这个pydantic有一个方法可以直接使用，便于管理和同步）

有考虑到失败重试的问题，但一阶段只考虑到了网络波动重试和pydantic校验不通过重试。网络波动重试设定了max_retries进行指数退避模式的等待重试， pydantic校验不通过重试则是将失败的feedback作为prompt带入到上下文，让llm知道上次校验失败是因为什么原因，下次避开。而针对OPENAIERROR比如可能有模型不存在啊、APIkey错误之类的问题，以及其他异常则不重试直接break，进入兜底的结果返回。

## 问题发生和对应解决
### 一阶段

上线测试后，应用侧进行了小批量并发请求调用智能体。150项审计任务共涉及约400项规则审查任务，其中有6项规则审查任务出现了```length limit was reached```，其对应的审计任务在数据库里的状态也没有更新，一直处于running状态。查看log发现这6个审计任务都是相比于完整走完的节点，因为存在执行失败的规则子任务，直接判定审计异常，输出固定模板总结，走完了所有的图节点。但是没有图结束的log，正常完成的会有“Langgraph审查工作流执行完成”的log以及后续回调。17:26:03开始出现调用大模型错误```length limit was reached```，但是之前在16:52就已经开始报```asyncio.exceptions.CancelledError ```。判断应该是规则审查节点陷入了死循环，而一阶段未对大模型设置max_tokens，默认输出是打满的，所以打满了256k的总token。由于此前的log对于报错的情况输仅输出报错信息，且这些任务因为提前被ARQ因为超时删除了导致没有落库（不过原来对于失败的任务也不会将整体的审计结果落库来着），所以不知道是什么原因导致的打满token。所以在该阶段我做了如下措施：

1. 补充max_tokens设置，暂且设置了4096。还设置了requests_time。
2. 由于不确定是因为json内部出现的死循环还是json输出结束后又有什么其他的文字说明陷入了死循环，于是我尝试加入了stop词，并且prompt里面加上了对应的设定，要求json输出完以后补充上stop词。
3. 捕获cancellederror报错后更新数据库状态和上报回调。保证任务超时时我的任务状态会变为失败而不是一直在running。 同时对于已经接收入库但是进入redis队列失败的情况我也做了捕获，重试后直接上报任务失败。

### 二阶段
再次上线测试，并且进行了小批量并发请求调用。仍是同一批任务，有4项规则出现了```length limit was reached```，超过了4096的上线（不过这次审计任务闭环了，有对失败状态进行更新和上报）。那很明显stop词并没有用，应该是都没有机会到输出stop词，说明是json内部死循环，很有可能是列表符号等原因。但是它也没有走到失败重试那边，说明和pydantic校验也无关。其实一阶段当时没有仔细看log，没有注意到是OPENAI SDK raise的错误（报了CompletionUsage），这回知道了是走到了OPENAI的分支，查了了解到具体的error是LengthFinishReasonError。那么就有了以下二阶段措施：

1. 去掉stop词和相关的prompt
2. 优化prompt，限制列表长度。
3. **LLM 参数与基础配置优化**：
   - 全局默认温度设为 `TEMPERATURE=0.1`，保证财务合规审计在绝大多数场景下的高确定性与严谨性；
4. **精细化重试分流机制**：
   - **Token 长度超限 / 死循环 (`LengthFinishReasonError` / `length limit was reached`) - 两级渐进式退避**：
     - **Attempt 1 (初次)**: `temperature=0.1`, `frequency_penalty=0.0`
     - **Attempt 2 (第1次重试)**: 保持干净上下文，温度微调升至 `0.2`，通过微小采样随机性尝试跳出贪婪解码死循环；
     - **Attempt 3 (第2次重试)**: 保持干净上下文，温度微调升至 `0.3`；
     - **Attempt 4 (第3次重试)**: 温度维持在 `0.3`，动态 `bind(frequency_penalty=0.1)` 激活频率惩罚，精准打击复读死循环；
     - 严禁将长度报错带入 Prompt（避免污染上下文加剧幻觉/困惑）。
   - **Pydantic 格式/缺失校验失败 (`ValidationError` / `OutputParserException`)**：带入 `error_feedback` 反思提示，引导模型修正字段缺失。
   - **网络抖动 / 429 限流 (`APIConnectionError` / `APITimeoutError` / `RateLimitError`)**：保持上下文干净，进行指数退避 `time.sleep(2 ** attempt)` 休眠重试。
   - **系统不可恢复故障 (`AuthenticationError` / `BadRequestError` 等)**：直接 `break` 终止，走入兜底流程。
5. **日志排查强化**：
   - 在截断异常发生时，提取异常对象中的生成片段（`raw_completion_snippet`），便于后续精准定位截断内容。


那么针对token长度超限的参数设计，理由如下：
1. 审计场景下要求合规严谨，所以我们初始温度都设置得很低在0.1，以防止llm自由发挥。大模型预测下一个 Token 时，Logits 经过温度缩放计算概率：
    $$P(w_i) = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$
    但是在温度极低的情况下，概率分布极度尖锐，采样几乎退化为贪婪搜索，如果模型由于局部上下文相关性陷入了某种复读或不断生成列表项的状态，已生成的重复词会作为历史上下文进一步加剧下一个相同词的注意力权重，形成正反馈“死循环”。重试时采用动态递增温度（范围限制在0.3以下），对温度在推理严谨的范围内进行微调，引入极小的概率扰动，降低死循环的可能性。
2. 在温度达到0.3的情况下，若仍还未跳出死循环，说明模型陷入了复读，此时加入极低的频率惩罚，压制长句、大段列表的无线衍生。频率惩罚根据token在已生成文本中出现的绝对频次，对logit施加线性压抑。若最开始就去调整frequency_penalty，有可能破坏json语法结构导致漏打标点或者拼写变形。

> 详细的内容我让llm做了个笔记
> #### 1. 采样温度梯次退避（Temperature: $0.1 \to 0.2 \to 0.3$）
> * **涉及核心概念**：
>   * **Softmax 温度调节（Temperature Scaling）**：大模型预测下一个 Token 时，Logits 经过温度缩放计算概率：
>
>    $$P(w_i) = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$
>
>   * **自回归退化 / 贪婪解码循环陷阱（Autoregressive Degeneration / Greedy Decoding Trap）**：当 $T$ 极低（如 0.1）时，概率分布极度尖锐，采样几乎退化为贪婪搜索（Greedy Search）。如果模型由于局部上下文相关性陷入了某种复读或不断生成列表项的状态，已生成的重复词会作为历史上下文**进一步加剧**下一个相同词的注意力权重，形成正反馈“死循环”。
>   * **探索与利用权衡（Exploration vs. Exploitation Trade-off）**。
> * **为什么这样调整是合理的？**
>   * **基准 $T=0.1$ 的合理性**：财务合规审计要求极高的确定性、一致性与事实依据，低温度可以最大程度抑制幻觉。
>   * **阶梯微调（$+0.1$ 递增至 $0.3$）的合理性**：如果发生截断（死循环），直接大幅调高温度（如调到 0.7~1.0）会导致审计结论不稳定甚至胡言乱语；而**微调至 0.2/0.3 依然属于严谨推理的低熵区间**，但引入了微小的概率扰动（Perturbation），足以帮助模型在关键分支点避开最高概率的死循环路径，跳出局部吸引子（Local Attractor）。
>---
> #### 2. 频率惩罚的滞后激活（Frequency Penalty: $0.0 \to 0.1$ 阶梯介入）
> * **涉及核心概念**：
>   * **Logit 频率惩罚项（Frequency Penalty Formulation）**：
>
>    $$z_i' = z_i - \alpha_{\text{freq}} \times \text{count}(w_i)$$
>
>   它根据 Token 在已生成文本中出现的绝对频次，对其 Logit 施加线性抑制。
> * **为什么这样调整是合理的？**
>   * **初次调用严禁开启（$\alpha_{\text{freq}}=0.0$）**：在 JSON 结构化输出场景中，标点符号（如 `"`、`{`、`}`、`:`、`,`）和 Schema 键名（如 `"risk_status"`、`"evidence"`、`"file_url"`）天然具有**极高频次的合法重复**。若一开始就开启频率惩罚，极易破坏 JSON 语法结构（导致漏打标点或拼写变形）。
>   * **第 4 次尝试（Attempt 4）才以 $0.1$ 激活**：当连续两次微调温度仍未跳出循环时，说明模型陷入了顽固语义级别的长文本复读。此时以 $0.1$ 的微弱惩罚介入，既能压制长句/大段列表的无限衍生，又不会摧毁短距离 JSON 语法的构建能力。
