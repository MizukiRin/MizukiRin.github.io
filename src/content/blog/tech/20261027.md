## PART 1 LLM生成的置信度是真的有把握吗

我们都知道，置信度是指对结果的把握程度。在统计机器学习里，计算出结论某量值为a的概率是x，置信度是y，那我们就是有y的把握该量有x的概率值为a。就像乾贞治在说海棠会往左移动的概率是100%时，他的置信度通常是0.99+（x

在大语言模型输出文本时，它是根据当前语境下，统计词表空间里每个字符的概率分布。

### 文本自生成
当我们通过提示词要求LLM“请输出判断及置信度”，它生成出`{"result":"有利", "confidence":0.95}`，本质是一个token续写。基于预训练的海量语料库数据，注意力机制检索到前文的内容都很顺畅再加上人类给出的报告数据通常是0.95，模型觉得此处出现“0.95”的概率高它就输出出来的，这是文本自生成的结果。模型根本不知道自己究竟多有信心，它输出纯粹是因为这个数字最像一个专业的回答。

而推理模型在输出置信度文本的时候可能会更加极端一点，它在输出最终答案之前已经在<think>里面做了深度的推导甚至反思，当它被要求输出置信度时，注意力机制会聚焦在自己的思考论述中，这种时候它们几乎都会特别自信。

>强化学习（RL）的奖励信号通常绑定的是“答案对不对”，从未奖励过“诚实评估自身不确定性”。这就导致模型在 RL 策略优化后，表达风格被训练得极具确定性。


### logprobs
对数概率（logprob）是指大型语言模型在其输出中给定位置的token所分配的概率的对数。本质是模型内部激活值概率，模型最后一层注意力加权向量经 Linear Head 映射到 Vocabulary 后得到未归一化的原始打分logits，经 Softmax 归一化再取自然对数$\ln$ 的结果，反映了模型内部当前神经元激活的确定性程度。对数概率越接近于0，模型对该token的置信度就越高。通常会取指数将其还原为普通概率。

同样的例子，我们要通过大模型来判断某材料是否对我方有利。我们约束模型只能输出两个候选词：`有`和`不`，在调用模型时带上`logprobs=True`参数，将会收到包含每个token底层概率的词典。通过logprobs提取到的首词概率即可认为是该结论的置信度。当大模型无法判断材料是否有利或不利时，会表现出摇摆不定的状态。这两者的概率会很接近。

普通模型输出结论的概率是基于用户输入而产生，而推理模型的最终答案的概率是基于用户输入和前面的详细思考过程。当思维链已经定下，无论是极度简单规则还是强行圆上的逻辑，最后答案那个词的logprob都会被打满，我们无法再通过它的大小去分辨它是十拿九稳还是强行狡辩。

要注意的是，Logprob衡量的是根据上下文生成这个token的概率而不是“这条规则在逻辑上是否成立”，如果它理解错材料里的某项规定或者把两份单据的主体搞反了，在它内部的注意力权重看来根据他的理解（可能是错误的），这里必须是xxxx。它可以在100%笃定的状态下输出完全错误的结论。

> 某些高频正面词汇（如“是”、“合规”、“正确”）在预训练语料中的自然概率天然就高于否定词（如“否”、“违规”）。哪怕面对一段含糊不清的材料，模型输出【合规】的 baseline Logprob 可能本身就比【违规】高出好几倍，这完全是语料词频带来的噪音，没有任何业务意义。

### 采样一致性投票
那单一生成结果不可靠，那改成重复采样N次计数是不是就可靠了？但这也同样消耗了N倍算力与延迟。同样的输入、同样的prompt，并且把温度调高如0.7，给每次采样引入随机性。同样是判断某材料是否有利的场景，如果材料本身非常清晰，哪怕有随机干扰，10次里也会有9次甚至10次输出“有利”；如果材料本身模棱两可，就有可能五五开。在该方式下，置信度即为输出次数占总采样次数的占比。这也是三种方式里面统计学意义最强的一种。

## PART 2 JEV里的置信度
与通用大模型的文本续写不同，JEV 是决策模型，面向的是确定性图路由与决策分支，它将决策与自由文本生成解耦，其置信度来自决策层的概率映射与校准机制（如 RLCD）。

### choice - 离散分支选择
choice的置信度是受约束的分类后验概率，对应所选分支的归一化softmax概率。模型直接对用户定义的离散分支计算后验概率，并且在RLCD训练阶段就引入了校准误差惩罚（防止过于尖锐的softmax分布）。这意味当jev给出一个choice且置信度为0.75时，在统计学意义上，历史同类输入的真实命中率高度收敛于75%。

### score - 连续评估
在评估某项指标强度时，score的置信度衡量的是该评分的确定性程度。JEV 打分是预测分值的概率密度分布，分值是该分布的均值/期望，而置信度是该分布的集中程度（由离散度如香农熵或后验方差反向计算得出）。分布越尖锐（方差极小），置信度越趋近于 1；分布越平坦或出现多峰，置信度越低。


## PART 3 LLM文本情形判断
其实会提出【LLM的置信度是否真的可信】这样的问题是因为几次收到的一些利用LLM进行复杂文本判定的需求或者方案时，出现了输出【置信度】的值（比如高中低）的需求。虽然个人是觉得这样不合理的但还是想说找寻一下相关资料来作证，遂有了以上的查询。 

通常涉及到的agent场景包含合同合规审查、报销票据审核、法律文书审查等。这类场景的核心在于辅助决策与事实可追溯，相比于模型给出一个概率数字，证据链本身就完成了置信度的表达，也更加可靠可供人类验证。只要模型给出的推断逻辑闭环、原文证据存在，该判定的置信度在人类眼中就是100%；反之如果证据是伪造的，哪怕模型标了0.99的置信度也毫无意义。同样的，若强行生成一个置信度的数字，反而容易让下游业务产生疑问。比如在有明确证据链的情况下，是难以解释为什么同样的材料昨天是0.85今天是0.82。

长文本规则判定的重点在于多处分散证据的交叉印证、例外条款的覆盖和边界模糊情形的定性。既然摒弃了这种无意义的置信度打分，我们该如何真正在工程上保障大模型在长文本判定时的准确率？ 这就涉及到了大模型的底层工作机制。

大模型的本质是自回归生成，这就导致了一个风险即事后合理化。如果模型在输出的第一句话就过早地下了结论，那么它后续生成的所有解释都会强依赖于前面这个结论的注意力权重。由于日常项目可选模型十分有限，所以当我们在做这种判定时，针对不同模型有不同的prompt策略。 
 - 普通轻量模型（flash）/关闭thinking的混合模型：适用于简单审核和快速比对场景。由于没有预先的推断，若任它自由发挥极易一上来就抢答结论导致误判。故在实践中，通过强约束的JSON schema，让模型先输出推论，最终写结论。利用模型生成的分析token来充当外部工作记忆，这样单次向前传播就能命中到正确的逻辑分支，降低幻觉和过早下定论的风险。
  - 推理模型/开启thinking的混合模型：自带隐式推演，在正式输出前有进行多方面的逻辑推断，适合复杂长文本交叉对比。面对这类模型逻辑校验已经在`<think>`内完成了，完全可以采用结论先行输出的方式。 

如果在模型可选且没有严苛的吞吐和延迟要求下，我们一般选择推理模型来做审查审计任务，使判断逻辑更加严密。普通轻量模型更多的还是用在需要及时反馈的问答场景中的简单判断和意图识别，比如“该用户提问是否为办理事项相关”、“当前输入是否存在敏感问题”。

> 顺便提一嘴在RAG的总结节点，使用推理模型通常会陷入过度思考之中，不仅响应极慢还可能会试图在无关片段中建立逻辑自洽。RAG属于外部检索工程而前面提到的长文本审查场景属于内部跨度推断。RAG相当于把“找证据”的动作前置了，后续只需要进行简单的信息缝合任务，不需要复杂逻辑推演，此时非推理模型反而能更好的做提取、润色和输出的动作。

## PART 4 JEV落地 - 真假复杂语义
JEV出来的时候，我也在考虑能否将JEV接入问答场景，正好最近有个决策图谱接入的预研，遂进行尝试。在“该用户提问是否为办理事项相关”、“当前输入是否存在敏感问题”这两个判定节点里，JEV表现不错，再加上有统计意义的置信度，其结论比轻量语言模型更可靠些。但我重点关注的还是该能力是否能用在决策图谱下钻场景。

这个场景的核心在于如何让模型比对用户本轮输入的文本和节点信息（本节点的内容和后续子节点结构）是否满足自动下钻到下一节点。

### 第一轮
在最开始的测试实验中，我选择的是noul原语，`question`是“下钻”，分支是`是`和`否`。造的test case有三类，第一类是用户给出了明确身份/细分条件，当前节点信息只是概括，需要继续下钻；第二类是当前节点信息已经给出详尽、闭环答案，无需下钻；第三类是用户输入极其模糊/多分支互斥，不能盲目下钻，必须停在当前节点抛选项。

设计的question如下：
```
pay_load = {
        "model": "typesafe/jev-1.14",
        "state": state,
        "questions": {
            "need_drill_down": { 
                "type": "noul",
                "instructions": "结合分支结构信息（`state.structure`） 判断当前的回答 `state.node_info` 是否能完全解决用户问题`state.user_query`，且后续结构中存在更明确符合用户诉求的子业务，需要进一步向下钻取。认为用户输入的信息不足以满足判断，则直接视为不下钻",
                "criteria": {
                    "true": "当前节点的 node_info 仅为总括性描述或未解决用户核心诉求，且 structure 中明确列出了能进一步精确解答该问题的子业务，可以继续深入下钻。",
                    "false": "当前节点的 node_info 已经直接回答了用户的核心疑问；或者用户的输入条件过于笼统或模糊或无法断定走哪个分支，不应当下钻。"
                }
            }
        }
    }

```


问题出现在第三类，举个例子如下：

它的结论下钻是0.65，不下钻是0.35。也就是说即使我在question里面声明了模糊场景的不下钻的情况，模型的结论仍处于摇摆不定。

这时候就在想，会不会是不下钻的原因有两种，一种是当前节点已经能满足了不需要下钻了，另一种是信息缺失需要人提供更多信息所以不下钻。于是改成用choice开始了第二轮实验。


### 第二轮
在第二轮，把question拆成了如下三种动作，一种是直接回答、一种下钻、一种是需要选择：
```
pay_load = {
        "model": "typesafe/jev-1.14",
        "state": state,
        "questions": {
            "next_action": {
                "type": "choice",
                "instructions": "结合当前节点信息 `state.node_info` 与后续分支结构 `state.structure`，评估对用户当前问题 `state.user_query` 应采取的最优下一步动作。",
                "criteria": {
                    "direct_answer": "当前节点的 node_info 已经充分、完整地回答了用户的核心疑问，无需且不宜继续下钻，直接向用户输出当前答案。",
                    "drill_down": "用户提问指向非常精准，当前节点信息仅为大纲，且 structure 中明确存在能更深入解答该诉求的具体子业务分支，应自动继续向下钻取。",
                    "need_selection": "用户的提问较为笼统或未提供关键前置条件，当前节点无法直接回答，且后续存在多个互斥的子分支，不应盲目猜测，需停留在当前节点并向用户展示选项。"
                }
            }
        }
    }
```
在本实验中，此前第三类问题，即用户模糊输入无法判定下钻场景均能很好的指向`need_selection`分支，且置信度都在0.9以上。

根据这个结果其实会发现一件事情，模型在判断时进行了两个部分的核验，首先核验是否满足办理条件，其次核验用户的需求信息。三个case对应了三个结论：①在用户输入和待比较的信息里能够完全都能对应上时，模型判断有极高的置信度。②当首要条件不满足时，模型的结果不会受次要核验内容的影响；③当用户输入缺失明确指向的信息时，置信度极低。

CASE54里，“有哪些办理途径”这七个字，它是一个“枚举型”提问，而不是“单点操作型”提问：
  - 想选 drill_down（0.48）：因为具体的途径就在下级的两个子分支里，模型觉得不往后钻就拿不到具体途径名称。
  - 想选 need_selection（0.23）：因为一共有“线上”和“窗口”两个渠道，既然用户问有哪些，前端展示两个按钮卡片给用户选是最合理的交互。
  - 想选 direct_answer（0.29）：当前节点已经回答了核心门槛（满六个月方可取消），如果把当前节点直接回答“可以通过线上或线下渠道办理”，在常识上也讲得通。

在经过讨论后意识到，可能是因为我们把“信息充分度（认知层面）”和“下一步给文本还是给按钮（交互层面）”强行塞进了一个 Choice 题里，导致不同层面的逻辑互相打架。

于是有了第四轮的实验。

### 第四轮
在这一轮，把question拆解成两个方向，一个是判断当前节点能否回答用户的问题，一个是评估后续行动指向。
```
pay_load = {
        "model": "typesafe/jev-1.14",
        "state": state,
        "questions": {
            "is_sufficient": {
                "type": "noul",
                "instructions": "判断当前节点的信息 `state.node_info` 是否已能够回答用户的问题（包括政策资格、时限要求、办理结论等）。",
                "criteria": {
                    "true": "当前节点已直接解答了用户的疑问",
                    "false": "当前节点完全未涉及用户的核心问题，必须借助后续子分支 `state.structure` 中的流程信息。"
                }
            },

            "specificity": {
                "type": "choice",
                "instructions": "结合后续分支 `state.structure`，评估用户的提问指向方式。",
                "criteria": {
                    "single_target": "用户明确指向了 structure 中的某一个特定子业务分支。", 
                    "multi_target": "用户询问整体办理途径/概览，或者其诉求同时涵盖了后续多个子分支。",
                    "vague_unknown": "用户输入非常笼统或缺失关键前提，完全无法判断与哪个分支相关。"
                }
            }
        }
    }
```
但是本轮结果反而在CASE53上表现很差。不光`specificity`置信度低，连`is_sufficient`也误判成false。

针对`is_sufficient`做了以下分析和调整:因为没有直接出现“你只办了一个月，所以你不能撤销”这句话，JEV 在字面严格比对时，认为当前节点没有直接给出否定结论，因而判了 False。于是在`is_sufficient`的`true`选项补充了`或者用户在询问是否可以办理某业务，而当前信息已经明确列出了条件，足以做出合规判断。`后，再次进行测试，CASE53判定为true，没想到此时CASE54被判断为true了————模型看到了“满八个月”和“需满六个月”，它以为用户在问时限，于是判了 True。但用户真正问的是“有哪些途径”，途径根本没回答。

而对于`specificity`，CASE53用户在问“能不能撤销”，这三个选项全都是在问“去哪个分支办”。大模型发现没有任何一个选项能完美对应用户的问题，只能勉强在 multi_target (0.61) 和 single_target (0.22) 之间分摊概率，置信度自然暴跌到了0.41。

### 真假复杂语义
无论怎么改都越来越乱，我开始思考一个事情：jev是不是要求对问题和选项原子化，即单个简单问题和选项带有简单条件且每个选项不产生冲突不模糊。这些问题和选项需要满足：
  - 单一维度：一个问题只测度文本的一个物理属性。
  - 选项之间不能有任何语义重叠。（既可以理解为 A，又可以理解为 B）
  - 单跳直觉匹配，JEV 擅长的是直接特征感知

让ai帮我根据以上原则重新生成的question如下：
```
"questions": {
    // 原子问题 1：用户的提问意图类型（互斥 3 选 1）
    "query_type": {
        "type": "choice",
        "instructions": "判断用户当前提问的疑问类型。",
        "criteria": {
            "eligibility": "用户在询问自己是否符合办理条件/能否办理（如‘能马上撤销吗’、‘需要交满几年’）。",
            "operation": "用户有明确办理意图，询问具体的办理步骤、入口或操作方式（如‘怎么撤销’、‘每一步怎么操作’）。",
            "overview": "用户询问该事项整体包含哪些途径、有哪些政策概况（如‘有哪些办理途径’、‘分为哪几种情况’）。"
        }
    },
    // 原子问题 2：用户是否在输入中显式指定了某个办理渠道？（互斥 3 选 1）
    "channel_mentioned": {
        "type": "choice",
        "instructions": "用户本次希望办理的渠道指向。",
        "criteria": {
            "online_app": "用户明确要求在手机、微信小程序或国家医保平台APP线上操作。",
            "offline_window": "用户明确要求前往各区医保中心线下经办窗口现场办理。",
            "none_or_unspecified": "用户未指定本次办理渠道，或者询问有哪些渠道。"
        }
    }
}
```

可以发现，这个原子问题被拆得特别的定制化，针对了我刚刚CASE51-54的用户输入和节点信息进行了拆解改写。但是我们无法寄希望于用户每次输入都在这个设计范围内，节点信息也多变也不光光是在讲渠道。最开始的时候，我的思路是设计通用的question，无论是“是否能够下钻”、“结合分支判断往哪个业务分支走”、“节点信息是否能够回答用户问题”，它看上去是个二分类问题或者是有限选项的问题，但现在再带入进去看会发现，不光用户输入是变化的，问题也是变化的，这二者一结合成了动态场景，判断“能否下钻”的背后隐含了无数个小问题和语义问题。下钻表面上是一个二分类，本质上是一个复杂的阅读理解推导题，它必须综合：用户当前真实身份 + 用户口语表达的真实诉求 + 当前节点的信息+ 后续子节点的排他性关系。它的评估标准是随节点的跳转而随时剧烈变化的。我们人类以为的简单判断问题实际上是复杂语义。

JEV 缺乏多步思维链推理，必然在各种复杂的边界场景上频繁翻车、置信度低迷，我们要用JEV满足回答“是否能够下钻”这个问题，就要把它拆为每一个要点的判断。我们不可能穷尽预设好所有的question，就需要引入LLM来做这样的原子问题设计拆解。但是，有必要吗？直接利用LLM的动态上下文理解和推理能力，把变化的用户信息和变化的 节点信息当作知识背景塞给大模型，大模型天然能在语义层面上做逻辑闭环。

那么JEV的适用场景就清晰明了了，即无论用户输入如何，规则恒定不变的场景，如：
  1. 安全检查：无论是办医保还是办入学，全系统对 Prompt 注入、SQL 攻击、越狱、违法暴恐的判定标准全生命周期 100% 恒定。
  2. 简单意图判断：判定是“政务与公共服务咨询”还是“纯闲聊打趣、写代码、查天气”，也是一套全系统通用的判别标准。

> 还蛮有趣的。在《思考，快与慢》中讲到系统1是毫不费力的直觉而系统2是推断。JEV是system-one模型，而我开始也以为“是否下钻”这种是可以毫不费力回答的问题。通过这个实验也意识到，会不会是我们人类在做“简单”二分类问题判断时自以为没有在思考比较是直接凭直觉经验进行的判断，但实际上在这极短暂的过程中我们做了快速的问题拆解、数据提取和比对从而得出结论？或者也有可能是因为我看多了这样的case或者有相关的场景经验，把原来需要的推理内化成了我的直觉？如果拿这种下钻场景的语料去训练system-one模型，是否也能做到内化成直觉？或许有时间可以试试。
