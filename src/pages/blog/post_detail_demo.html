系统架构设计师备考指南：系统规划篇

2026-05-12
Tech Blog
8 min read

在软考高级“系统架构设计师”的考纲中，系统规划往往是被很多技术出身的考生忽略的部分。大部分人习惯于一上来就看微服务设计、数据库调优或者高并发架构，但系统规划决定了项目的商业价值和立项逻辑。

排斥冗余的业务包装并不意味着不需要理解业务目标。恰恰相反，只有理清了系统规划的底层逻辑，才能在后续的架构选型中做到有的放矢，避免过度设计。

一、 企业信息化与架构对齐

架构不是凭空产生的，它必须对齐企业的战略目标。在考试中，常见的考点集中在“战略数据规划”和“企业架构（EA）”模型。

  • Zachman 框架：最经典的分类法。从谁（Who）、什么（What）、为什么（Why）、时间（When）、地点（Where）、如何（How）六个维度，结合不同的视角（规划者、所有者、设计者等）构成矩阵。
  • TOGAF：关注点在架构开发方法（ADM），分为业务架构、数据架构、应用架构和技术架构。
“系统架构师不应仅仅是高级程序员，而应该是能够将业务痛点翻译为技术路线图的桥梁。”

二、 可行性分析的核心逻辑

可行性分析是系统规划的输出结果，主要包含四个维度的评估。考试中经常出现判断某项活动属于哪个可行性维度的选择题。

  • 经济可行性：成本收益分析（CBA）、投资回报率（ROI）。
  • 技术可行性：当前技术栈能否支撑目标，风险有多大。
  • 法律可行性：合规性、知识产权、数据出境等问题。
  • 用户使用可行性：组织的管理模式是否排斥新系统，用户的接受度如何。

三、 简单的数据流图（DFD）与代码映射

在规划阶段后期，我们通常会使用 DFD 来初步描绘系统边界。虽然这是古老的方法论，但其核心思想与现代的微服务边界划分依然相通。

例如，下面这段简单的 Python 数据处理流水线伪代码，本质上就是在代码层面落实数据流和转换节点： 

from typing import List, Dict

class DataProcessor:
    def __init__(self, raw_data: List[Dict]):
        self.raw_data = raw_data
        self.cleaned_data = []

    def run_pipeline(self) -> None:
        """执行核心清洗流水线"""
        for record in self.raw_data:
            if self._validate(record):
                transformed = self._transform(record)
                self.cleaned_data.append(transformed)
        
        self._load_to_db(self.cleaned_data)

    def _validate(self, record: Dict) -> bool:
        # 对应 DFD 中的过滤节点
        return record.get('status') == 'active'

    def _transform(self, record: Dict) -> Dict:
        # 对应 DFD 中的加工节点
        record['normalized_score'] = record['score'] / 100.0
        return record

    def _load_to_db(self, data: List[Dict]) -> None:
        # 对应 DFD 中的数据存储节点
        pass

理解 _validate 和 _transform 这样的函数，就像理解 DFD 里的圆圈（加工进程）一样。不要觉得理论考试空洞，将其映射到你熟悉的 Python 或 SQL 逻辑中，理解起来会非常迅速。

小结

系统规划的难点不在于技术深度，而在于视角的转换。尝试跳出 IDE，站在项目发起人的角度看问题。下一篇笔记，我将整理关于“软件架构风格”的考点与踩坑记录。
